1. Executive Summary & Strategic Focus

While the Systrome Wireless Access Controller (WAC) supports heterogeneous multi-vendor infrastructure (Cisco, Aruba, TP-Link Omada, Ubiquiti UniFi, and Ruijie), native Systrome Wireless Access Points are the Tier-1 first-class citizen of the platform.

By tailoring a modern, open, and lightweight communication protocol directly to Systrome AP hardware and firmware (running OpenWrt / Systrome OS), we achieve four distinct operational advantages:

  • Zero-Touch Provisioning (ZTP): Brand-new APs boot from factory, auto-discover the WAC, authenticate via cryptographic certificates, and self-configure with zero manual intervention.
  • Sub-Second Real-Time Telemetry & Observability: Real-time channel utilization, client roaming, RF spectrum noise, and instant offline alerts via MQTT Pub/Sub.
  • Declarative Device-Twin Configuration: A GitOps-style "Desired State vs. Reported State" engine with transactional validation, safe-mode watchdog, and automatic rollback to prevent branch lockouts.
  • Decoupled Control & Data Planes: Control and orchestration use lightweight MQTT over TLS, while client data traffic uses either high-speed Local Bridging (Direct Breakout) or scalable VXLAN/WireGuard tunnels for centralized corporate policies.

2. Technology Evaluation: SNMP vs. CAPWAP vs. MQTT vs. WebSockets

Network architects frequently evaluate whether traditional carrier protocols (CAPWAP, SNMP) or modern edge IoT protocols (MQTT, WebSockets) should govern the AP fleet. Below is an exhaustive engineering comparison:

Evaluation Dimension SNMP (v2c / v3) CAPWAP (RFC 5415/5416) MQTT over TLS (Selected)
Communication Model Inbound Request/Response polling + UDP Traps State-machine Client/Server over UDP Asynchronous Pub/Sub Message Broker
Transport & Ports UDP 161 (Poll), UDP 162 (Trap) UDP 5246 (Control), UDP 5247 (Data) TCP 8883 (MQTTS) or TCP 1883
NAT & Firewall Traversal Extremely Poor: Controller cannot poll an AP behind a NAT gateway without public IP or VPN. Fragile: Stateful firewalls drop UDP keepalives; severe Path MTU (PMTU) & fragmentation drops. Native & Flawless: AP initiates an outbound TCP TLS session to broker. Works seamlessly behind NAT, CGNAT, 4G/5G WAN.
Configuration Delivery Inadequate: SNMP SET lacks transactional multi-object consistency, schema validation, and rollbacks. Complex & Rigid: Proprietary vendor TLVs; rigid binary byte structures; difficult to extend. Declarative JSON: Clean JSON payloads applied transactionally to OpenWrt /etc/config/ via uci.
Telemetry & Metrics Latency High Latency (1–5 min): Periodic polling of 1,000 APs overloads controller CPU and network bandwidth. Bundled: Integrated into keepalive packets; inflexible schema changes. Sub-Second Stream: AP streams radio utilization, client stats, and RF noise floor at customizable intervals.
Offline Detection Slow: Detects failure only after multiple poll timeouts (3–10 minutes). Moderate: Echo interval timeouts (15–30 seconds). Instant (< 1 sec): Last Will and Testament (LWT) automatically triggered by broker upon socket disconnect.
AP RAM & CPU Footprint Low (snmpd daemon). High (Complex DTLS crypto engine, packet fragmentation buffers). Ultra-Low (< 4 MB RAM): Minimal C/Go/Python agent footprint; runs on low-cost MIPS/ARM APs.
Data Plane Encapsulation None (Management only). Integrated UDP 5247 Split-MAC tunnel. Decoupled: Local Breakout by default; pair with VXLAN / WireGuard for centralized tunneling.
Architectural Decision for Systrome Wireless: MQTT over TLS is selected as the primary Control & Monitoring plane for all Systrome APs. Data forwarding is decoupled via Local VLAN Breakout (wire-speed switching on the AP) with optional VXLAN/WireGuard tunnels for centralized campus isolation. Native 802.1X/RADIUS (FreeRADIUS) on UDP 1812/1813 handles authentication directly between AP hostapd and the WAC AAA cluster.

4. Core Operational Flows & Device Lifecycle

4.1. Zero-Touch Provisioning (ZTP) & AP Onboarding

  1. Power On & Network Acquisition: AP connects to PoE switch, obtains IP address and DHCP Option 43 (specifying wac.systrome.net or MQTT broker IP). If Option 43 is omitted, it falls back to DNS resolution.
  2. Cryptographic TLS Session: AP initiates an outbound TLS handshake on port 8883 using its factory-burned x509 client certificate.
  3. LWT Registration: During the MQTT connect packet, the agent sets its Last Will and Testament: 
    systrome/ap/{mac}/status -> {"state": "OFFLINE", "reason": "CONNECTION_LOST"}
  4. Registration Announce: AP publishes hardware inventory: 
    systrome/ap/{mac}/status -> {"state": "JOINING", "model": "SAP-6000AX", "firmware": "v2.1.4"}
  5. WAC Registration & Provisioning: WAC creates/updates the AP record in PostgreSQL, assigns the AP Group profile, pushes the desired configuration, and transitions state to ONLINE.

4.2. Declarative Device Twin Configuration Flow

The WAC never issues blind bash scripts. Instead, it follows the industry-standard Device Twin pattern:

[Administrator edits SSID in UI] │ ▼ [WAC Core generates JSON delta] │ ▼ (Publish QoS 1 to systrome/ap/{mac}/config/desired) [systrome-agent receives desired configuration] │ ├── Validate JSON schema against hardware capabilities ├── Backup current UCI files to /tmp/backup_cfg ├── Apply parameters: uci set wireless.@wifi-iface[...] ├── Commit & Reload: uci commit && wifi reload │ ▼ [Safe-Mode Watchdog Timer (45 seconds)] ├── Ping WAC MQTT broker over WAN │ ├── SUCCESS -> Commit config, publish IN_SYNC to config/reported │ └── FAILURE -> Revert from /tmp/backup_cfg && wifi reload (Auto Rollback!)

4.3. Real-Time Telemetry & Event Stream

  • Periodic Metrics (every 30s): Ingested on systrome/ap/{mac}/telemetry containing CPU usage, RAM utilization, board temperature, per-radio channel utilization (%), noise floor (dBm), and active client SNR.
  • Asynchronous Events (Instant): Ingested on systrome/ap/{mac}/events containing 802.11 client association/disassociation, 802.11k/v/r fast roams, 5 GHz DFS radar strikes, and rogue BSSID alarms.

4.4. Dual-Bank Safe FOTA Firmware Upgrades

Systrome APs utilize dual-bank A/B flash partitions. The WAC sends an RPC upgrade command specifying binary URL and SHA-256 hash. The AP writes to the inactive bank, sets U-Boot counter to 3, and reboots. If the new image connects to WAC within 120s, the partition is committed permanently; if it crashes, hardware watchdog reboots back into the previous known-good bank!

8. Rust Services Engineering Roadmap: AP Agent & Controller Listener

To satisfy carrier-grade throughput, strict memory limits on embedded hardware, and zero-garbage-collection predictability, both the AP-Side Firmware Service and the Controller Ingestion Listener are specified in Rust.

8.2. Service 1: AP-Side Agent Architecture (systrome-agent-rs)

Designed as an embedded async daemon running under OpenWrt procd.

Modular Crate Structure:
  • agent-core: Tokio async runtime (tokio with minimal feature set), POSIX signal handling (graceful SIGTERM/SIGINT), supervisor integration.
  • agent-mqtt:
    • Pure async Rust MQTT client via rumqttc.
    • TLS encryption via rustls (removes OpenSSL dynamic library dependency on the AP).
    • Automatic reconnection with exponential backoff (1s, 2s, 4s... max 60s).
    • Last Will & Testament (LWT) configured on systrome/ap/{mac}/status.
  • agent-telemetry:
    • High-efficiency asynchronous /proc reader (/proc/stat, /proc/meminfo, /proc/net/dev).
    • OpenWrt ubus IPC integration (via direct UNIX domain socket /var/run/ubus/ubus.sock) querying iwinfo info (channel, noise floor, airtime) and hostapd.<iface> get_clients (connected client MAC, RSSI, SNR, PHY rates).
  • agent-config (Device Twin & Watchdog):
    • Deserializes desired JSON payload into strongly typed Rust structs (serde).
    • Generates OpenWrt UCI transactions (/etc/config/wireless, /etc/config/network).
    • Safe-Mode Watchdog: Spawns an async tokio::time::sleep(Duration::from_secs(45)) task. If gateway WAN ping fails within the window, executes atomic UCI rollback and issues status: ROLLBACK_TRIGGERED.
  • agent-rpc:
    • Handles immediate commands: REBOOT_AP, LOCATE_BEACON (GPIO LED sysfs trigger), TRIGGER_SPEEDTEST, and DISCONNECT_CLIENT.

Target Cross-Compilation Matrix:

├── mips-unknown-linux-musl (Older Atheros / MediaTek MIPS 24Kc APs) ├── mipsel-unknown-linux-musl (MediaTek MT7621 / MT7628 APs) ├── armv7-unknown-linux-musleabihf (Qualcomm IPQ4019 / IPQ6000 Wi-Fi 5/6 APs) └── aarch64-unknown-linux-musl (Qualcomm IPQ8072 / MediaTek Filogic Wi-Fi 6E/7 APs)

8.3. Service 2: Controller Ingestion Listener (wac-mqtt-listener-rs)

A multi-threaded, high-concurrency ingestion gateway deployed alongside the Express API in the WAC cluster.

Modular Listener Components:
  • listener-consumer: High-speed async consumer using rumqttc::AsyncClient. Subscribes to systrome/ap/+/status, telemetry, events, config/reported, and rpc/response. Ingests into an internal ring buffer (tokio::sync::mpsc::channel(50000)).
  • batch-pipeline & db-writer: Buffers incoming telemetry into micro-batches (e.g., max 500 records or 100ms window). Uses sqlx with a PostgreSQL connection pool (PgPool) to perform bulk multi-row operations: AP status, CPU, RAM, last_seen_at, and radio channel/noise floor updates.
  • redis-broadcaster: Asynchronously publishes telemetry and status changes to Redis Channels (systrome:ap:events, systrome:ap:telemetry) via fred-rs. Express Node.js WebSocket Hub listens to Redis and relays instantly to active browser sessions.
  • grpc-control-server (Internal IPC): Exposes a high-speed gRPC server (tonic) on an internal port (127.0.0.1:50051). When an administrator deploys configuration in the Web Console, Express makes a fast gRPC call, and the listener signs and publishes the payload to systrome/ap/{mac}/config/desired via MQTT QoS 1.

9. Summary & Architectural Conclusions

By replacing heavy runtimes with Rust for both the AP-Side Agent and the Controller MQTT Listener:

  • On the AP: We achieve sub-2.5 MB RAM consumption and zero external dependencies, making Systrome APs the leanest and most resilient hardware on the market.
  • On the Controller: We eliminate Node.js event-loop bottlenecks and garbage collection pauses, enabling a single standard server instance to ingest real-time telemetry from over 50,000 active Systrome APs.
  • On the Network: MQTT over TLS provides effortless NAT traversal, instant offline alerting (LWT), and safe declarative configuration with automated rollback.

By centering the WAC on MQTT over TLS + OpenWrt UCI/Ubus for Systrome APs:

  • We solve all NAT/firewall traversal issues without needing complex VPNs or public AP IPs.
  • We achieve instant offline detection via MQTT Last Will and Testament.
  • We achieve sub-second telemetry without crushing the controller under periodic SNMP poll cycles.
  • We maintain a clean separation between the Control Plane (MQTT) and the Data Plane (Local Breakout or VXLAN), delivering the fastest, most scalable wireless controller experience on the market.
